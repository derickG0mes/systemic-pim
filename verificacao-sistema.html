Prontidão para app Android/iOS · Fase 7

Estado atual: a API aceita JWT Bearer, mas o login observado entrega o token somente em cookie HttpOnly. Não há fluxo móvel de emissão de token, refresh ou revogação identificado.

Rotas existentes por tela

  • Login: GET /api/Autenticacao/csrf, POST /api/Autenticacao/login, GET /api/Autenticacao/validar, POST /api/Autenticacao/logout.
  • Mesas: /api/Mesa (listar, obter por ID, CRUD; escrita restrita).
  • Comandas: /api/Comanda, /abertas/todas, /mesa/{tableNumber}, itens, pagamento, fechamento e inadimplência.
  • Pedidos: /api/Pedidos, detalhe, criação, atualização, status e exclusão.
  • Produtos: /api/Produto, detalhe, CRUD e ajuste de estoque.
  • Reservas: /api/Reserva (listar, criar, cancelar).

As rotas principais de mesas, comandas, pedidos, produtos e reservas existem. O front não usa APIs de Cliente e FormaPagamento, operações de escrita/detalhe de Mesa, vários endpoints de detalhe/itens/fechamento de Comanda, listagem/detalhe/exclusão de Pedidos e operações de despesas. O contrato não foi certificado com fluxo feliz em todas as ações.

Ordem de trabalho de menor risco

  1. Adicionar fluxo Bearer sem remover o cookie web: endpoint de token, access token curto, refresh rotativo armazenado com segurança no servidor e logout/revogação.
  2. Manter CSRF obrigatório em autenticação por cookie; avaliar tratamento explícito para Bearer nas mutações, preservando a proteção CSRF do navegador. Não abrir CORS com wildcard junto de credenciais.
  3. Adicionar paginação, ordenação, filtros e limites de payload nas listas; hoje várias respostas materializam listas completas.
  4. Completar telas e serviços front para Cliente/FormaPagamento, detalhes e operações ausentes; acrescentar estados loading/error em telas como Pedidos e Reservas.
  5. Remover logs de payload/retorno de pedidos do console do navegador e revisar dados pessoais expostos em logs.
  6. Repetir JWT adulterado/expirado, SignalR após restart da API e faturamento contra SQL manual sob dados controlados.

CORS/CSRF: clientes nativos normalmente não dependem de CORS do navegador; com cookie, devem manter CSRF. A validação antiforgery global também se aplica hoje a chamadas mutáveis com Bearer; qualquer exceção precisa ser explícita e testada. CORS deve continuar restrito a origens web confiáveis.

Paginação/payload: paginação observada em logs (pagina/tamanho); a maioria das listas principais não tem paginação ou filtros consistentes. Tamanho máximo de payload por tela não foi medido. Erros/loading: inspeção estática encontrou pedidos sem estado explícito de erro/loading e reservas sem estado de carregamento; outras telas mostram toasts/indicadores parciais.
